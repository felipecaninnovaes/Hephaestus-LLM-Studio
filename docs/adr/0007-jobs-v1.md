## Contexto

A primeira fatia vertical de **jobs** atravessa todos os boundaries de uma vez:
o usuário cria um dataset YOLO, clica em **Treinar**, e um job `yolo_train` flui
principal → manager (fila) → orquestrador-local (build + execução) → engine
`trainer-yolo` **mock (CPU)** → artefatos de volta → painel de jobs + telemetria
real da sidebar. Hoje esses serviços são skeletons de 12 linhas (só `GET /health`),
o `trainer-yolo` só imprime um JSON de health (sem modo treino), e a UI tem os
ganchos desabilitados honestos (Sidebar telemetria "—", botão Treinar disabled).
O schema §10 **já projeta** `jobs`/`job_artifacts`/`job_samples`/`runners`/
`orchestrators`/`dataset_versions`, mas nada foi migrado (a 3e encerrou em 54/54
testes de banco com 0005). Esta ADR decide **quais tabelas nascem na migration 0006**,
o formato do package, os contratos internos principal↔manager↔orquestrador, a
telemetria sem GPU e o escopo exato da v1 — o resto fica registrado como adiado.

Regras da casa aplicadas: wire camelCase em `/api/*`, transporte/manifests
snake_case (ADR-0002 D1); `404 not_found` para id não-UUID (ADR-0002 D8);
erros `{code,message}` com `message` estática (`src/error.rs`); engine mock atrás
de `ENGINE_MOCK=1` com default seguro; GPU real só `@gpu` manual fora do compose;
PRs < ~400 linhas de produção; branch `feat/jobs-v1`.

## Decisões

### D0 — Escopo v1 exato (entra/sai) e a fatia de jobs como slice vertical único

**Decidido — entra na v1:** `yolo_train` LOCAL end-to-end com engine mock:
`POST /api/datasets/:id/package` + `POST /api/jobs/yolo` + `GET /api/jobs` +
`GET /api/jobs/queue` + `GET /api/jobs/:id` + `POST /api/jobs/:id/abort` +
`GET /api/jobs/:id/metrics` + `GET /api/jobs/:id/artifacts` (+ `.../data`) +
`GET /api/telemetry` (polling); migration 0006; cliente S3 escopado no
orquestrador; `trainer-yolo` mock com modo treino; UI (Treinar + painel `/jobs` +
telemetria da sidebar). Ficam construídas na v1 (estrutura migrada e ciclo
completo) ainda que a superfície só exponha o subconjunto acima: fila com
`queue_reason`, ciclo completo, snapshot `dataset_versions`, `job_artifacts`.

**Decidido — fora da v1 (adiado, registrado para fatias futuras):**
- **remoto/RunPod** e **transporte chunked ADR-0003 D9** (`package/init`,
  `package/:id/chunk/:i`, `package/:id/complete`) — o consumidor (orquestrador
  remoto) não existe na v1; o `files[].key` e `chunks` do manifest ficam
  ausentes/`null` no transporte local (D1). *Rationale:* código sem consumidor é
  a lição P1 da ADR-0006.
- **difusao_train / clip_train / autolabel / autotracker / playground /
  download_model** — a v1 só aceita `engine=yolo` (`engine_unsupported` 400 nos
  demais).
- **runners warm (§5)** e **`POST /runners/*`** — playground fora.
- **pause / resume / checkpoint** — a v1 NÃO expõe `POST /:id/pause|resume`
  (sem engine de checkpoint); expõe **apenas `abort`**. O `409 checkpoint_unsupported`
  só nasce quando houver engine de checkpoint. *Gotcha:* o §9 lista pause/resume —
  fica marcado como adiado no §"O que fica falso nos docs".
- **samples por ciclo (§7)** — o mock **não gera `samples/`** (gerar imagem fake
  seria desonesto; sem imagem real no mock). `GET /:id/samples` **não entra** no
  contrato v1 (fica no §9 como pendente; `job_samples` não migra — D1).
- **multi-GPU/DDP** (§6/:92) — 1 job = 1 GPU no futuro; v1 local single-node.
- **WS** `/ws/jobs/:id/logs` e `/ws/telemetry` — polling no lugar (D9); WS/logs
  ficam para a fatia de logging/WS.

**Descartado:** entregar só um "job enfileirado" sem execução real (não provaria
o pipeline); expor pause/resume "por causa do §9" sem checkpoint (rota morta e
mentirosa); mock emitir samples falsas.

### D1 — Quais tabelas nascem na migration 0006; formato do package v1 (zip autossuficiente)

**Decidido — migration `0006_jobs.sql` cria 4 tabelas** (DDL no §"Migration 0006"
abaixo, colunas à letra do §10):
- **`orchestrators`** — incluída: `jobs.orchestrator_id` tem FK; a auto-adoção do
  `orchestrator-local` e a telemetria/heartbeat gravam nela.
- **`jobs`** — incluída: núcleo da fatia; `dataset_id` FK `ON DELETE SET NULL` (T4).
- **`job_artifacts`** — incluída: retorno de artefatos (D4/D8).
- **`dataset_versions`** — incluída: snapshot do T4 (D1a).
- **Adiadas:** `job_samples` (v1 não gera samples), `runners` (playground fora),
  `models` (download de modelos fora). *Justificativa:* tabelas mortas só para
  "DDL estático" virariam schema sem escrita; quando a fatia correspondente
  chegar, as FKs CASCADE vêm na própria migration (padrão 3b `videos` foi a
  exceção porque a 3b precisava da FK irmã — aqui nada referencia `job_samples`/
  `runners`/`models` na v1). *Gotcha:* `orchestrators` e `jobs` nascem juntas para
  a FK `jobs.orchestrator_id → orchestrators(id)` existir desde o primeiro INSERT.

**Decidido — formato do package v1 (D1a):** o package é um **zip autossuficiente**
(imagens + `labels/*.txt` + `dataset.yaml` com lists `train`/`val` + `config.yaml`
separado) mais um `manifest.json` de transporte — **não** referências soltas a
keys canônicas. *Rationale:* backend.md §4/:62 "entrada do trainer = **zip** do §3
+ config.yaml"; e permite escopar a credencial S3 do orquestrador a **`packages/*`**
sem ler `datasets/*` (D2). Pipeline do package (reuso do builder da 3e):

1. `POST /api/datasets/:id/package` congela **`dataset_versions{manifest}`** (JSONB
   snake_case: `{dataset{id,slug,category,engine}, classes[], images[{filename,
   split,width,height,boxes[],caption?}], counts}` — a "trava lógica por versão"
   de §10/:258) e devolve o `versionId`.
2. Materializa a árvore do engine **do banco** em tempdir (refatorar
   `src/datasets/export.rs` para extrair o builder de materialização YOLO —
   doutrina "o package sempre gera do banco", §10/:257; split do `images.split`).
3. Gera o zip (mesmas regras da 3e: `Stored` p/ imagens, `Deflated` p/ texto) e
   `PUT` em **`packages/<dataset_version_id>/dataset.zip`** + `manifest.json`.
4. `manifest.json` (transporte §11): `{dataset_id, slug, category, engine,
   files:[{filename,md5,bytes}] (entradas do zip), md5_zip, bytes,
   chunks: null, created_at}`. **Na v1**: `files[].key` ausente (não há leitura
   por objeto) e `chunks: null` — nascem com o orquestrador remoto (ADR-0003 D9).
5. Job submission chama o mesmo builder (função compartilhada, não a rota) antes
   de enfileirar; a rota pública existe para uso standalone e teste.

**Descartado:** manifest só com referências a keys canônicas `datasets/{id}/`
(o orquestrador precisaria ler `datasets/` → amplia a credencial e viola o escopo
mínimo de D2; e §4 manda zip); zip em RAM (tempdir, memória constante — 3e D2);
package em `job.params` sem snapshot durável (perderia a trava por versão do T4).

**Decidido (D1b) — donos:** `dataset_versions` e o package são **do principal**
(domínio de dataset; o principal é o único com o builder e a leitura do banco).
O manager **não** cria snapshot. Correlação `job ↔ dataset_versions` é **frouxa**:
sem FK no §10; o package vive em `packages/<dataset_version_id>/` e o `job.params`
JSONB carrega `package_ref` (snake_case) `{version_id, key, md5_zip, bytes}` para
o manager persistir o suficiente para re-despachar no boot. *Gotcha* registrado:
correlação via `params.package_ref` — documentar na sync (R7). *Residual:* o sweep
do `DELETE /:id` cobre `datasets/{id}/`, não `packages/<version_id>/` — packages
de dataset deletado viram objeto órfão no bucket (R6).

### D2 — Credencial S3 do orquestrador: identidade dedicada escopada por prefixo no SeaweedFS

**Decidido:** nova identidade **`heph-orchestrator`** em `infra/seaweedfs-s3.json`
com accessKey/secret dedicados (LOCAL-DEV, não o `heph-admin`) e actions
**escopadas por path** no `-s3.config` (formato nativo do SeaweedFS — evidência
verificada: wiki "S3 Configuration" + `weed/s3api/policy_engine/examples.go`,
identidades legacy `"Read:bucket1/*"`, `"Write:bucket1/*"`, `"List:bucket1"`;
o PR #10192 que corrigiu wildcard de prefixo foi no caminho **IAM inline**
(`-s3.iam.config`), não no `-s3.config`):
- `Read:heph-data/packages/*`, `List:heph-data/packages/*` (ler o zip + manifest)
- `Read:heph-data/artifacts/*`, `Write:heph-data/artifacts/*`,
  `List:heph-data/artifacts/*` (devolver artefatos)
- **Sem** acesso a `datasets/*`, **sem** `Admin`/`UserManagement`/`Tagging`/`Admin:*`.

**Invariante de código no orquestrador (segunda barreira):** toda key S3 passa por
um helper central que prefixa com o escopo permitido (`packages/` ou `artifacts/`)
e **recusa** qualquer key fora do prefixo (proteção contra path-traversal via
manifest malicioso). O orquestrador **não pode ler `datasets/`**.

Envs novos no `orchestrator-local` (compose): `S3_ORCH_ENDPOINT_URL`,
`S3_ORCH_BUCKET` (default `heph-data`), `S3_ORCH_ACCESS_KEY`, `S3_ORCH_SECRET_KEY`,
`ORCH_WORKDIR` (`/data`), `EXEC_MODE` (já existe). Fail-fast no boot sem ecoar valor
(padrão `load_storage` do principal).

**Decidido — Dockerfile:** só o **orquestrador** migra `bookworm-slim` →
`trixie-slim` (aws-lc-sys, GLIBC_2.38). O **manager** **não** ganha S3 na v1 e
**mantém** `bookworm-slim` (documentar; ver nota dividas :113-117). *Gotcha:*
o `List` é bucket-level no SeaweedFS (testes `TestBucketLevelListPermissions`,
issue #7066) — **não está provado** que `List:heph-data/packages/*` autoriza
`ListObjectsV2` com `prefix=packages/` (ver R1 + Spike F4.0); se exigir
`List:heph-data` a nível de bucket, conceder só `List` (vaza nomes de objetos,
não conteúdo) e registrar residual.

**Descartado:** dar ao orquestrador o `heph-admin` (derrota o escopo mínimo);
credencial por-job (complexidade sem necessidade local); confiar só no escopo do
SeaweedFS sem a barreira de prefixo no código (defesa em profundidade).

### D3 — Contrato principal↔manager (interno, fora do OpenAPI público)

**Decidido:** rotas internas do manager (Bearer `MANAGER_TOKEN`), **snake_case**
(transporte, não `/api/*`):
- `POST /internal/jobs` — cria job enfileirado. Body: `{kind, engine, model, mode,
  dataset_id, dataset_version_id, package_ref{version_id,key,md5_zip,bytes},
  config_yaml, params, vram_min_gb}` → `202 {job_id, status:"queued"}`; manager
  insere `jobs` (status `queued`, `queue_reason NULL`) e responde.
- `GET /internal/jobs` — lista (com `queue_position`/`queue_reason` por job).
- `GET /internal/jobs/:id` — estado atual (poll da UI passa pelo principal BFF).
- `POST /internal/jobs/:id/abort` — marca `cancelling` e notifica o orquestrador.
- `POST /internal/jobs/:id/report` — **push** de progresso do orquestrador (D4).
- `POST /internal/heartbeat` — telemetria/heartbeat do orquestrador (D4/D9).
- Manager indisponível/falha na chamada → o principal responde `503
  queue_unavailable` no `POST /api/jobs/yolo`.

**Decidido — auto-adoção:** no boot o manager auto-adota **`orchestrator-local`**
(INSERT em `orchestrators` se ausente: `kind=local`, `endpoint=http://
orchestrator-local:8082`, `status=online`); sem chave (rede docker), health-check
15s/2 falhas = `degraded`, 5 = `offline` (§8/:109). **Recuperação de fila no boot**
(§1/:33): manager relê `jobs` com `status IN (queued,dispatched,preparing,running)`
→ marca `queued` com `queue_reason='recovered'` e re-despacha.

**Descartado:** manager com client S3 ou Postgres-write em tabelas de dataset
(viola §1/:32); dispatch via principal (manager fala direto com o orquestrador);
estado de fila só em memória (viola resiliência §1/:33).

### D4 — Contrato manager↔orquestrador (despacho, report push, heartbeat)

**Decidido:**
- **Despacho:** manager → orquestrador `POST /internal/dispatch` (rede docker,
  Bearer opcional na v1 local — §8/:103 auto-adoção sem chave) body `{job_id,
  engine, image, exec_mode, package_ref{key,md5_zip,bytes}, config_yaml,
  dataset_version_id, workdir}` → `202`. Orquestrador recusa (409/400) se já tem
  job `preparing/running` com o mesmo `job_id` (idempotência anti-duplo-despacho — R4).
- **Report de progresso: PUSH** (não polling): orquestrador → manager
  `POST /internal/jobs/:id/report` a cada evento — `{status: preparing|running|
  done|failed, progress, epoch, step, metrics?, error?, artifacts?}`.
  Transições de status são gravadas pelo **manager** (dono de `jobs`); o
  orquestrador nunca toca o Postgres.
- **Heartbeat:** orquestrador → manager `POST /internal/heartbeat`
  `{gpus:[], vram_total, vram_used, cpu, ram, jobs_active}` a cada ~2s; manager
  atualiza `orchestrators.last_heartbeat` + cache de telemetria (serve D9).
- **Artefatos:** no report `done`, o orquestrador envia `artifacts:
  [{kind, path, md5, bytes}]` (JÁ enviados ao bucket `artifacts/<job_id>/`, D8);
  o manager valida a lista, insere `job_artifacts`, grava `metrics` e marca o job
  `done` com `finished_at`.

**Descartado:** polling manager→orquestrador para progresso (PUSH é o desenho
§1/:34 "artefatos voltam via POST do orquestrador"; polling adiciona latência e
estado); orquestrador escrevendo no Postgres (stateless §1/:29).

### D5 — Engine mock trainer-yolo v1 (modo treino simulado + modo real @gpu documentado)

**Decidido:** o `trainer-yolo` ganha o comando
`python -m trainer_yolo train --config <config.yaml> --output <output_path>`
(entry `trainer-yolo-train` no pyproject — espelho verificado do
`trainer-clip-serve` em `engines/trainer-clip/pyproject.toml:14-15`).
Com `ENGINE_MOCK=1` (default), simula: lê `config.yaml` (model/epochs/batch/imgsz/
lr0/optimizer/augment), itera `epochs` com sleep curto (~100–300 ms), grava
`metrics.jsonl` (1 linha por epoch: `box_loss, cls_loss, dfl_loss, mAP50,
mAP50-95, epoch`) e, ao final, grava artefatos **fake** (`best.pt`/`last.pt` com
bytes de cabeçalho determinístico) em `output_path`. **Não** gera `samples/` (D0).
Sem `ENGINE_MOCK` + GPU = modo real `@gpu` manual **documentado** (não no compose):
import lazy de `ultralytics` (extras `[train]` no pyproject), comando equivalente
`yolo train data=... model=...`; a doc diz como plugar. `metrics.jsonl` → o
orquestrador lê e envia ao manager como `metrics` (D4).

**Decidido — Dockerfile novo `engines/trainer-yolo/Dockerfile`**
(`python:3.12-slim` pinado, stdlib puro no mock, sem pip install — padrão
`trainer-clip` 3f.3, verificado no Dockerfile existente) e build da imagem
`hephaestus/trainer-yolo:local` no compose (serviço de build; F4.6). Execução:
`EXEC_MODE=docker` (padrão do compose.yaml, via `/var/run/docker.sock` do host)
ou `subprocess` (venv com o pacote; caminho do RunPod sem socket, §11/:270) —
**v1 verificado em `docker`**; `subprocess` implementado atrás do env, não é o
caminho de aceite (R5). Atenção: `compose.integ.yaml` hoje força
`EXEC_MODE: subprocess` — o F4.6 alinha ao veredito do spike (docker se passar).

**Descartado:** mock que só devolve métricas sem iterar épocas (não exercitaria
progress/epoch/step); gerar imagem fake de sample (desonesto); instalar ultralytics
na imagem base (mock é stdlib puro, GPU real é `@gpu`).

### D6 — config.yaml e validação de hiperparâmetros (quem gera, o que valida)

**Decidido:** o **principal** gera o `config.yaml` por job (responsabilidade
"geração e gestão dos JSON/YAML de configuração de treino" — IDEIA §1/:14) e o
envia ao manager (coluna `jobs.config_yaml`) e daí ao orquestrador. Shape
§11/:263-264:
- comum: `{job_id, engine, model, mode, dataset_path, output_path, seed}` — com
  `dataset_path`/`output_path` como **placeholders** (`{dataset_path}`/
  `{output_path}`) que o **orquestrador** substitui pelos mounts reais do container
  no momento do spawn (o principal é agnóstico de paths locais);
- yolo: `{model, epochs, batch, imgsz, lr0, optimizer, augment:{mosaic,
  mixup_flip}}`.

Validação do `POST /api/jobs/yolo` (400 `invalid_request`): `model` ∈ allowed
(`yolo11n|yolo11m|yolo11x|yolov9-c|yolo11-seg` — alinhado ao frontend.md §6.1 e
ao vram-table), `epochs` 1..=1000, `batch` ∈ {8,16,32,64}, `imgsz` ∈ {416,640,1024},
`lr0` 1e-5..=1e-1, `optimizer` ∈ {AdamW,SGD,Muon}, `augment` bools, `seed` opcional.
Wire camelCase: `{datasetId, model, epochs?, batch?, imgsz?, lr0?, optimizer?,
augment?, seed?}`. `datasetId` não-UUID/inexistente → 404 (D8); dataset não-pronto
→ 409 `dataset_not_ready` (D7).

**Descartado:** orquestrador montando o config do zero (principal é o gerador de
config, IDEIA §1); validação só no front (server-side é a casa — `models.rs`
validações puras).

### D7 — API pública v1 (delta OpenAPI 0.7.0) e erros novos

**Decidido — rotas novas (entram em `PROTECTED_ROUTES` com status exatos):**

```
POST /api/datasets/:id/package                        200 400 401 404 503
POST /api/jobs/yolo                                   202 400 401 404 409 503
GET  /api/jobs                                        200 401
GET  /api/jobs/queue                                  200 401
GET  /api/jobs/:id                                    200 401 404
POST /api/jobs/:id/abort                              200 401 404 409
GET  /api/jobs/:id/metrics                            200 401 404
GET  /api/jobs/:id/artifacts                          200 401 404
GET  /api/jobs/:id/artifacts/:artifactId/data         200 401 404 503
GET  /api/telemetry                                   200 401
```

- `POST /:id/package` — body `{engine}` (200 = `PackageResponse{versionId,key,
  bytes,md5Zip,files}`); 400 `invalid_request` (JSON malformado/campos
  desconhecidos) | 400 `engine_unsupported` (engine ≠ yolo na v1 — único uso
  real do erro nesta fatia) | 404 | 503 `storage_unavailable`.
- `POST /api/jobs/yolo` — 202 `{jobId,status:"queued",queuePosition?}`; 400
  `invalid_request` (params; a rota é fixa `/yolo` — o body NÃO carrega engine,
  use `POST /:id/package` para ver o `engine_unsupported`); 404 dataset;
  409 `dataset_not_ready` (category≠yolo, 0 classes, ou 0 imagens ativas); 503
  `queue_unavailable`.
- `GET /api/jobs` — 200 `{items:[Job],total}` (filtros opcionais `?status&engine`).
- `GET /api/jobs/queue` — 200 `{items:[{jobId,position,queueReason}]}` (fila
  ordenada; espelha §9 `GET /api/jobs/queue`).
- `GET /api/jobs/:id` — 200 `Job` (status, progress, epoch, step, metrics?,
  queuePosition, queueReason, createdAt, finishedAt); 404.
- `POST /api/jobs/:id/abort` — 200 `{status:"cancelling"|"cancelled"}`; 409
  `job_not_abortable` se terminal (done/failed/cancelled).
- `GET /api/jobs/:id/metrics` — 200 `JobMetrics` (série por epoch, camelCase:
  `{items:[{epoch,boxLoss,clsLoss,dflLoss,map50,map5095}]}` — nota de contrato:
  mAP50-95 vira `map5095` no wire, camelCase-safe, documentar no spec); 404.
- `GET /api/jobs/:id/artifacts` — 200 `{items:[{id,kind,path,md5,bytes}]}`; 404.
- `GET /api/jobs/:id/artifacts/:artifactId/data` — 200 `application/octet-stream`
  (proxy do objeto, espelho do `/images/:imageId/data`); 404 | 503.
- `GET /api/telemetry` — 200 `Telemetry` (D9).

**Erros novos** (em `error.rs` + enum do spec): `queue_unavailable` (503),
`dataset_not_ready` (409), `job_not_abortable` (409), `engine_unsupported` (400).
Reuso: `invalid_request` (400), `not_found` (404, id não-UUID — D8),
`storage_unavailable` (503, ADR-0003 D10). **Não entram na v1:** pause/resume,
samples, WS. Wire camelCase global; `jobs.metrics` JSONB é snake_case (transporte)
e o principal re-mapeia para camelCase no response (D1).

**Descartado:** `409 checkpoint_unsupported` na v1 (não há checkpoint — rota nem
existe); expor `/api/jobs/queue` duplicando `GET /api/jobs` (barato e honesto ao
§9); 422 para validação (a casa usa 400 `invalid_request`, ADR-0005 D8).

### D8 — Artefatos de volta e quem escreve `job_artifacts`

**Decidido:** os artefatos são escritos pelo **orquestrador** no bucket
(`artifacts/<job_id>/best.pt|last.pt|metrics.jsonl` — credencial escopada
`artifacts/*`, D2); o **manager** (dono de `jobs`) insere as linhas `job_artifacts`
a partir do report `done` do orquestrador. `md5` é calculado pelo orquestrador no
upload (é o único com os bytes locais) e registrado; o manager não re-baixa para
verificar na v1 (R10). `GET .../artifacts/:id/data` do principal faz proxy do
objeto com o bucket (credencial admin) e pode conferir o `md5` sob demanda.
`path` = key relativa ao prefixo `artifacts/<job_id>/`.

**Descartado:** orquestrador escrevendo no Postgres (stateless); principal
escrevendo `job_artifacts` (tabela do manager, §1/:32); artefatos só em volume
sem ir ao bucket (o volume `outputs` é o cache do container; o retorno ao bucket
é o que permite o principal servir e sobreviver a restart).

### D9 — Telemetria v1: polling (sem WS) + VRAM ausente = no-op com aviso honesto

**Decidido:** expor `GET /api/telemetry` (polling, sidebar a cada ~3s), **sem**
`WS /ws/telemetry` na v1. Fonte: o orquestrador faz `heartbeat` ~2s (D4) com
`cpu`/`ram` reais (leitura do `/proc` do container orquestrador — aproxima o host em Linux single-node; documentar a limitação na sync F4.9) e `gpus:[]` (sem GPU no mock); o manager cacheia
e o principal serve `{measured:false, vramUsed:null, vramTotal:null, cpu, ram,
gpus:[], jobsActive}`. **Política VRAM sem GPU = no-op:** no mock não há
`waiting_vram` (telemetria `measured:false`), o job yolo passa direto da fila;
`vram-table.yaml` continua sendo a fonte quando GPU real existir (`@gpu`). A
sidebar mostra VRAM `"sem GPU (mock)"` em vez de inventar número, e CPU/RAM reais
(D10).

**Descartado:** `WS /ws/telemetry` na v1 (WS é a fatia de logging/WS); inventar
VRAM no mock (desonesto — dividas.md :132-136 pede telemetria real, e sem GPU a
real é `unmeasured`); bloquear fila por `vram_min` no mock (seria deadlock sem GPU).

```sql
-- 0006_jobs.sql — jobs/package/materialização (ADR-0007, fatia 4)
-- Ordem: orchestrators → dataset_versions → jobs → job_artifacts (FKs).

CREATE TABLE orchestrators (
  id UUID PRIMARY KEY,
  name TEXT NOT NULL,
  endpoint TEXT NOT NULL UNIQUE,
  kind TEXT NOT NULL CHECK (kind IN ('local', 'remoto')),
  fingerprint TEXT,
  token_hash TEXT,
  gpus JSONB,
  vram_total_gb INT CHECK (vram_total_gb IS NULL OR vram_total_gb >= 0),
  status TEXT NOT NULL DEFAULT 'unknown',
  last_heartbeat TIMESTAMPTZ
);
CREATE INDEX orchestrators_status ON orchestrators(status);

-- Snapshot do dataset no despacho do job (T4; nunca RESTRICT — ON DELETE CASCADE:
-- a versão morre com o dataset). Dono: principal (domínio de dataset).
CREATE TABLE dataset_versions (
  id UUID PRIMARY KEY,
  dataset_id UUID NOT NULL REFERENCES datasets(id) ON DELETE CASCADE,
  manifest JSONB NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX dataset_versions_dataset ON dataset_versions(dataset_id, created_at);

CREATE TABLE jobs (
  id UUID PRIMARY KEY,
  kind TEXT NOT NULL,
  dataset_id UUID NULL REFERENCES datasets(id) ON DELETE SET NULL,  -- T4
  engine TEXT NOT NULL,
  model TEXT NOT NULL,
  mode TEXT NOT NULL,
  params JSONB NOT NULL DEFAULT '{}'::jsonb,      -- inclui package_ref (D1b)
  config_yaml TEXT,                                -- config.yaml gerado pelo principal
  status TEXT NOT NULL DEFAULT 'queued'
    CHECK (status IN ('queued','dispatched','preparing','running','cancelling',
                      'done','failed','cancelled')),
  queue_reason TEXT,                               -- waiting_vram|waiting_slot|recovered
  orchestrator_id UUID NULL REFERENCES orchestrators(id) ON DELETE SET NULL,
  vram_min_gb INT CHECK (vram_min_gb IS NULL OR vram_min_gb >= 0),
  progress FLOAT CHECK (progress IS NULL OR (progress >= 0 AND progress <= 1)),
  epoch INT CHECK (epoch IS NULL OR epoch >= 0),
  step INT CHECK (step IS NULL OR step >= 0),
  metrics JSONB,                                   -- snake_case (transporte; D1)
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  finished_at TIMESTAMPTZ
);
CREATE INDEX jobs_status ON jobs(status);          -- exigido
CREATE INDEX jobs_dataset ON jobs(dataset_id);
CREATE INDEX jobs_created ON jobs(created_at);

CREATE TABLE job_artifacts (
  id UUID PRIMARY KEY,
  job_id UUID NOT NULL REFERENCES jobs(id) ON DELETE CASCADE,
  kind TEXT NOT NULL,
  path TEXT NOT NULL,
  md5 TEXT NOT NULL CHECK (md5 ~ '^[0-9a-f]{32}$'),
  bytes BIGINT NOT NULL CHECK (bytes >= 0)
);
CREATE INDEX job_artifacts_job ON job_artifacts(job_id);  -- exigido
```

Invariantes: `progress ∈ [0,1]`, `epoch/step ≥ 0`, `vram_min_gb ≥ 0` (CHECK
deferrável não necessário — são por-linha); `status` é o ciclo §4 (sem `paused`) mais o transitório `cancelling` (janela entre o abort aceito e a confirmação do orquestrador — D3/D7);
`queue_reason` é livre (motivos `waiting_vram|waiting_slot|recovered`). `kind`/
`engine`/`model` sem CHECK (crescimento livre entre engines). `jobs.dataset_id`
**SET NULL** e `jobs.orchestrator_id` **SET NULL** (nunca RESTRICT). `job_samples`/
`runners`/`models` NÃO migram (D1). Residual aceito: packages
`packages/<version_id>/` não são varridos pelo sweep do `DELETE /:id` (R6).

## Spike obrigatório? — **SIM (F4.0)**

Há premissas externas não verificadas (ao contrário da 3e): escopo por prefixo no
SeaweedFS, runtime trixie p/ aws-lc-sys, e docker-run de trainer a partir do
orquestrador. **Critérios binários e o que inverte:**
- **S3 prefix scope (4.45_full pinado):** `Write:heph-data/packages/*` autoriza
  PUT e `Read:heph-data/artifacts/*` autoriza GET (formato legacy do `-s3.config`
  é nativo — wiki + `policy_engine/examples.go`); **incógnita real: `List` em
  sub-prefixo** — o `List` é bucket-level no SeaweedFS (issue #7066/#7067
  corrigiu wildcards de bucket, não de sub-path; o PR #10192 corrigiu o caminho
  IAM inline, não o `-s3.config`). *Inverte:* se `List:heph-data/packages/*`
  não autorizar `ListObjectsV2` com `prefix=packages/` → conceder `List:heph-data`
  (bucket-level) e registrar residual de metadados; se o escopo por path estiver
  quebrado no 4.45 → fallback credencial dedicada `heph-orchestrator` com escopo
  só de bucket `heph-data` (Read+Write) + **invariante de prefixo no código como
  única barreira** (D2).
- **trixie-slim p/ aws-lc-sys:** build `aws-sdk-s3` no `debian:trixie-slim`
  (GLIBC 2.41) linka e roda. *Inverte:* pinar outro digest de trixie/rust-slim
  (R10 ADR-0003).
- **docker-run do trainer a partir do orquestrador (socket do host):**
  `docker run hephaestus/trainer-yolo:local` (imagem local) sobe e termina com o
  volume `outputs`. *Inverte:* se flaky/sem socket → `EXEC_MODE=subprocess`
  default, com o pacote trainer-yolo baked na imagem do orquestrador
  (F4.6/`compose.integ`).

## Resultados do spike F4.0 (2026-09-07 — matriz completa em `spike/JOBS-SPIKE.md`, branch `spike/jobs-f4-0`)

Executado na branch descartável `spike/jobs-f4-0` (NÃO mergeada; a matriz com evidência

   #7066 não afeta a imagem pinada). **D2 mantém o desenho** (identidade dedicada +
   actions por path); residual: contra Write/Delete em `packages/` e contra keys fora do
   escopo, a única barreira efetiva é o **invariante de prefixo no código do

2. **C2 — trixie-slim × aws-lc-sys:** troca CONFIRMADA como obrigatória. Binário
   construído em `rust:1.97.1-slim` (mesmo digest do projeto) roda em

3. **C3 — docker-run a partir de container (socket do host):** 3/3 runs exit 0,

## Riscos

- **R1 — Escopo por prefixo no SeaweedFS:** `Read/Write:heph-data/{packages,artifacts}/*`
  é nativo (verificado na wiki/examples.go); a incógnita é o `List` em sub-prefixo
  (bucket-level por design, issue #7066). Mitigação: spike F4.0 + invariante de
  prefixo no código como 2ª barreira; residual de metadados se `List:heph-data`
  for obrigatório.
- **R2 — GLIBC trixie / aws-lc-sys:** build do orquestrador pode exigir ajuste de
  digest. Spike F4.0; pinar digest.
- **R3 — Mock VRAM sem GPU:** fila não espera `waiting_vram`; telemetria
  `measured:false` honesta. Risco: alguém assumir VRAM real → documentar; `vram_min`
  gravado mas não bloqueante no mock.
- **R4 — Race de fila / dispatch duplo na recuperação de boot:** manager
  re-despacha jobs que o orquestrador pode já ter processado antes do crash.
  Mitigação: idempotência por `job_id` no orquestrador (recusa `preparing/running`
  do mesmo id) + report é upsert idempotente; advisory lock por job no manager.
- **R5 — Dispatch de container trainer (docker-from-orchestrator):** flaky/socket
  → fallback `subprocess` (spike F4.0).
- **R6 — Package duplica imagens no bucket por job** (zip autossuficiente):
  disco/CPU ×N; aceito local single-user; otimização futura (referências) fora da
  v1. **Residual adicional:** `packages/<version_id>/` não é varrido pelo sweep do
  `DELETE /:id` (escopo `datasets/{id}/`) — package de dataset deletado vira
  objeto órfão, reapável por script (stance da 3b).
- **R7 — Correlação job↔dataset_versions frouxa** (sem FK no §10): correlação via
  `params.package_ref` + prefixo `packages/<version_id>/`. Risco de drift se
  evoluir schema; documentar na sync.
- **R8 — Manager/principal indisponível:** `POST /api/jobs/yolo` → 503
  `queue_unavailable`; fila reconstruída no boot; consistência eventual.
- **R9 — Mock trainer não valida qualidade do modelo:** o critério E2E é de
  pipeline (job flui + artefato), não de mAP; documentar que o treino é simulado.
- **R10 — md5 de artefatos confiado ao orquestrador** (manager não re-baixa):
  residual aceito; principal pode conferir no proxy `.../data`.
- **R11 — `orchestrators`/`jobs` sem migration no manager:** as migrations são do
  principal (boot); manager depende do banco já migrado → `depends_on: principal`
